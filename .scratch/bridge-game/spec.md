# 局域网桥牌游戏开发规格

## Problem Statement

玩家希望和熟人通过浏览器打桥牌，即使真人不足四名也能开始和完成对局。玩家可能只有一人，也可能有两到四人在同一局域网内；他们不希望安装客户端、注册账号或依赖互联网。

游戏需要兼顾叫牌、打牌、计分和电脑补位，而非仅展示牌桌。掉线、刷新页面或服务重启后，已经完成的操作应保留；电脑牌手应遵守信息限制，并使用真人能够查阅的叫牌约定。

## Solution

在一台 Windows 电脑上部署桥牌 Web 服务。管理员解压服务端目录并双击启动后，即可获得局域网访问地址；玩家用电脑或手机浏览器打开地址，通过昵称和房间码进入独立房间。

房间提供东、南、西、北四个座位。房主开局时由电脑牌手填满空位，支持一名真人与三名电脑牌手的单机模式，也支持两到四名真人参与的局域网联机。两种方式使用相同规则、存档和恢复流程，运行时均无需互联网。

第一阶段交付完整可玩的基础版：简化自然叫牌、基本合理的电脑策略、每副独立计分、多房间、合法操作提示、对局记录及恢复能力。电脑达到普通牌友水平是后续提升目标，不把基础版通过功能验收等同于牌力达标。

## User Stories

### 访问与部署

1. 作为服务端管理员，我希望解压后双击启动服务，以便无需安装开发工具即可组织游戏。
2. 作为服务端管理员，我希望启动后看到局域网访问地址，以便发给同一网络内的玩家。
3. 作为服务端管理员，我希望程序与对局数据分开保存，以便更新程序时能够保留数据。
4. 作为真人牌手，我希望仅用浏览器访问游戏，以便无需安装客户端。
5. 作为真人牌手，我希望在没有互联网的局域网内游玩，以便游戏和电脑牌手不受外网影响。
6. 作为真人牌手，我希望界面使用简体中文，以便理解操作、状态和计分。
7. 作为真人牌手，我希望在电脑上舒适游玩，并能在手机上完成操作，以便使用手边设备参与。

### 房间与座位

8. 作为真人牌手，我希望使用昵称创建房间，以便邀请熟人游玩而无需注册账号。
9. 作为真人牌手，我希望通过房间码加入指定房间，以便进入朋友所在的牌桌。
10. 作为真人牌手，我希望同一房间内昵称不重复，以便辨认其他玩家。
11. 作为真人牌手，我希望自由选择东南西北座位，以便与朋友成为搭档或对手。
12. 作为房主，我希望控制何时开局，以便等准备参加的朋友就位。
13. 作为房主，我希望开局时空位自动由电脑牌手填满，以便人数不足也能游玩。
14. 作为独自游玩的真人牌手，我希望与三名电脑牌手完成一副牌，以便随时单机游玩。
15. 作为真人牌手，我希望不同房间的牌局彼此独立，以便多桌同时进行而互不影响。
16. 作为中途加入的真人牌手，我希望在下一副牌接替可用电脑座位，以便不改变正在进行的牌副。

### 叫牌与打牌

17. 作为真人牌手，我希望游戏完成发牌、叫牌、定约、打牌和结算，以便进行完整桥牌对局。
18. 作为真人牌手，我希望看到当前副号、发牌人、局况和行动方，以便理解对局进度。
19. 作为真人牌手，我希望界面提示合法操作，以便减少规则性误操作。
20. 作为真人牌手，我希望服务端拒绝非法或过期操作，以便所有参与者遵循同一牌局状态。
21. 作为真人牌手，我希望只有自己有权获知的信息被展示和传输给我，以便保持暗牌公平性。
22. 作为真人牌手，我希望查看完整叫牌记录和已发生的出牌记录，以便回顾公开信息。
23. 作为与电脑搭档的真人牌手，我希望电脑使用固定简化自然叫牌约定，以便理解双方的叫品。
24. 作为真人牌手，我希望在游戏内查阅中文叫牌约定表，以便知道电脑搭档采用的体系。
25. 作为真人牌手，我希望电脑牌手能叫牌、做庄和防守，以便任何空位都能补齐。
26. 作为真人牌手，我希望电脑只基于合法可见信息决策，以便电脑不会偷看暗牌或私下交换信息。
27. 作为真人牌手，我希望正常轮次不强制倒计时，以便有足够时间思考。

### 结算与继续

28. 作为真人牌手，我希望每副结束时看到得分明细，以便理解本副结果。
29. 作为真人牌手，我希望看到南北、东西双方累计分，以便了解当前房间的比分。
30. 作为真人牌手，我希望累计分按方位保留，即使中途换人也不清零，以便牌桌成绩连续。
31. 作为真人牌手，我希望一副结束后查看四家手牌，以便回顾结果。
32. 作为真人牌手，我希望确认准备后再开始下一副，以便有时间查看结算。
33. 作为真人牌手，我希望电脑自动准备，以便下一副不需要人为操作电脑座位。
34. 作为真人牌手，我希望发牌人和局况按固定 16 副周期轮换，以便连续游玩时保持一致安排。

### 暂停与恢复

35. 作为房主，我希望暂停和恢复整桌，以便处理临时事务。
36. 作为掉线的真人牌手，我希望获得 30 秒重连等待时间，以便短暂网络波动不会立即触发电脑接管。
37. 作为仍在线的真人牌手，我希望超过等待时间后由电脑接管掉线座位，以便牌局可以继续。
38. 作为重连的真人牌手，我希望同一浏览器能够恢复原身份和座位，以便继续参与自己的对局。
39. 作为重连的真人牌手，我希望在下一次需要该座位操作前取回控制，以便接续电脑已经完成的操作。
40. 作为原座位的真人牌手，我希望电脑接管期间座位仍为我保留，以便新玩家不会抢占我的位置。
41. 作为仍在线的真人牌手，我希望房主掉线满 30 秒后权限转交给最早加入且仍在线的真人，以便房间仍可管理。
42. 作为单机模式的真人牌手，我希望关闭页面后牌局自动暂停，以便回来时继续。
43. 作为真人牌手，我希望全部真人离线后立即暂停并保存，以便电脑不会自行打完牌局。
44. 作为真人牌手，我希望服务端保存每次完成的叫牌和出牌，以便不会因重启丢失已确认操作。
45. 作为房主，我希望服务重启或全员离线后恢复的牌局先保持暂停，待我确认继续，以便玩家有时间重新就位。

## Implementation Decisions

### 已确认架构

- 前端采用 React、TypeScript 和 Vite，使用 HTML/CSS 实现响应式牌桌；电脑浏览器优先，兼顾手机。
- 服务端采用受支持的 Node.js LTS、TypeScript 和 Fastify，统一提供页面、业务接口及局域网访问入口。
- Socket.IO 负责实时通信；SQLite 位于服务端本地磁盘，负责持久化牌局和操作记录。
- 页面、字体、图片、脚本及电脑运行依赖随服务端提供，运行时不访问外部 CDN、云模型或互联网服务。
- Windows 服务端目录附带运行环境与已构建页面，双击启动并显示访问地址；玩家端无需安装。数据与程序分离保存。
- 开发环境为 macOS，最终运行环境为 Windows。用户确认目标 Windows 电脑无需担心硬件性能，不将提供 Windows 硬件基线或确定性能阈值作为拆票前置条件；Windows 部署与离线运行仍须实际验证。
- 保留 10 桌含电脑决策的并发验证，重点检查多桌运行的功能稳定性；记录实际测试环境、耗时和资源占用，作为观察结果。

### 界面设计参考

采用用户通过 Open Design 制作的[柔和绿牌桌参考稿](../../design/references_classic.html)作为视觉与交互参考。参考稿覆盖入座、叫牌、打牌、明手、结算、公开记录及暂停提示。

- 以柔和绿色、清晰的东南西北座位、手牌区和侧栏为设计方向，沿用易读字号、明确的选牌反馈、合法操作提示及适合触控的按钮尺寸。
- 电脑浏览器优先，手机布局按可用宽度调整，保证本人手牌、明手和关键操作可见、可操作；无需逐像素复制桌面布局。
- 建房、房间码入房、中途加入等待、掉线接管和恢复等未完整覆盖的界面，沿用参考稿的视觉风格并按本规格补齐状态与交互。
- 参考稿内的电脑固定不叫、简化计分和页面内模拟状态仅用于演示。正式实现以本规格的叫牌、计分、服务端授权、持久化和恢复要求为准。
- 参考稿中的主题切换不新增为第一阶段必做功能；资源继续满足离线运行要求。

### 模块边界

- **对局应用服务**是主要业务入口：接收带身份的玩家操作，按房间顺序处理，调用规则、身份和存储能力，再返回可见状态。网络层和电脑牌手都通过这一入口推进对局。
- **桥牌规则模块**独立于界面、通信和存储，负责合法操作、牌局阶段、定约、打牌推进和计分。
- **房间与身份管理**负责昵称、房间码、座位归属、连接状态、房主及控制权；座位归属与当前由真人还是电脑操作分别表达。
- **电脑策略模块**接收合法可见信息，输出建议操作；它的操作仍由对局应用服务验证。接口可替换，以便后续接入更强引擎。
- **持久化能力**保存可恢复状态与操作记录，事务提交成功后才能向玩家确认成功和广播结果。
- **浏览器界面**提交意图并展示服务端确认的状态；合法操作提示不替代服务端校验。

### 房间与身份

- 每个房间四个座位，南北互为搭档、东西互为搭档。开局支持 1～4 名真人，空位由电脑牌手补齐。
- 昵称只用于展示和房间内防重，不能作为恢复身份的唯一凭据。服务端发放不可猜测的重连凭据，同一浏览器保留该凭据；连接标识与持久身份分开。
- 房间之间隔离身份授权、牌局、记录及累计分；知道房间码不等于有权操作某个座位。
- 当前副进行时，新玩家不能接替电脑。下一副只能接替未被真人占用的电脑座位；被电脑接管的原真人座位继续保留，直到原玩家主动退出，或房主在两副之间释放该离线座位。
- 第一版不提供旁观界面。中途加入者等待下一副的界面不得暴露当前副手牌。

### 完整牌副与计分

- 每副随机发牌，副号递增，并按固定 16 副周期确定发牌人和局况。
- 规则实现覆盖叫牌、定约与庄家确定、首攻、明手、跟牌、赢墩及结算。通行桥牌规则以 WBF 官方规则为参考，软件提前拒绝非法动作；不实现线下裁判纠违流程。
- 叫牌支持合法的 Pass、定约叫品、加倍和再加倍，处理全体不叫结束及定约成立后的流程。
- 庄家控制明手出牌；明手公开之前，各参与者只能获取有权获知的手牌。服务端授权同时校验当前轮次、行动的手牌和实际控制者。
- 每副独立计分并展示明细，覆盖定约完成、超墩、宕墩、局况及加倍状态带来的分数差异；南北和东西累计分按方位持续记录，采用正负对称展示。例如南北本副得 420 分，则南北累计增加 420，东西累计减少 420。
- 一副结束后可查看四家手牌。由真人控制的座位全部准备后开始下一副，电脑座位及已由电脑接管的离线座位自动准备；全员离线时仍保持暂停，不自动开新副。开新副时重置本副准备状态，不清零累计分。

### 电脑牌手与叫牌约定

- 已确认体系为五张高花、1NT 开叫 15～17 点、强 2♣、其余二阶花色弱开叫，包含基础应叫、Stayman 和高花转移叫。
- 中文约定表必须与电脑实际规则一致；第一版不提供自定义体系。具体牌型、点力区间、优先级、竞争叫牌及约定适用条件仍需形成明确规则表，见 Further Notes。
- 第一阶段使用规则驱动的叫牌和基础打牌策略，覆盖叫牌、做庄、首攻与防守，以规则正确和基本合理陪玩为目标。
- 电脑只使用自己手牌、依法公开的明手、局况及公开叫牌与出牌记录。若电脑控制庄家，接口应支持其合法控制明手的行为。
- 电脑可以推测暗牌，但不能接收实际暗牌、完整洗牌种子或其他可还原真实暗牌的内部数据；不同电脑不得私下共享各自手牌。
- 电脑运算与网络处理隔离，避免一桌思考阻塞其他房间。若引擎返回时状态已变化、牌局已暂停或控制权已转交，旧结果不能推进牌局。
- BEN、DDS 等更强方案为研究候选，未选定为基础版依赖；采用前需验证 Windows 运行、离线行为、叫牌约定匹配、分发条件和牌力。

### 操作与状态契约

- 操作至少包含房间标识、可验证的身份、唯一操作标识、预期状态版本及操作内容。叫牌、出牌、准备和管理操作都必须校验权限与阶段。
- 服务端按桌顺序处理操作，成功后生成新的状态版本。重复送达的同一操作不能重复出牌、累计分数或推进下一副。
- 服务端响应明确区分已接受、非法动作、无权限、过期状态和存储失败。客户端收到过期状态或重连后，重新获取该身份有权看到的当前状态。
- 每个玩家收到的是按身份生成的可见状态；暗牌不能先发给浏览器再依靠界面隐藏。实时推送、恢复快照、错误响应和对局记录遵循相同隔离规则。
- Socket.IO 的连接恢复只是辅助机制。持久身份、操作去重、状态版本和服务重启后的恢复由应用实现。
- 操作记录与相应牌局状态在同一事务中持久化，提交后才确认和广播。失败时不能让客户端认为操作已完成；重试不应造成重复应用。

### 暂停、掉线与控制权

- 正常操作不限时。房主可暂停整桌；暂停时真人操作和电脑结果都不能推进叫牌、出牌或自动开始下一副。
- 联机掉线等待 30 秒后由电脑接管。等待期内轮到该座位时应等待，其他本来就合法的操作可继续。
- 原玩家重连后，在下一次需要其座位操作前交还控制；已经提交的电脑操作不撤回，尚未提交的过期电脑结果应作废。
- 房主掉线满 30 秒后，将房主权限交给最早加入且仍在线的真人。全员离线后，原房主超过等待期仍未回归时，由已重连真人中加入最早者接任；权限转交不自动恢复牌局。
- 离线截止时间持久化并跨服务重启保留，不因重启重新计算已有的 30 秒等待期。重启时尚无离线记录的连接，从服务启动检测到其未连接时开始计时。
- 所有真人离线时立即暂停并保存，不继续电脑对局。这一规则优先于普通掉线接管规则；单机关闭页面属于此情形。
- 服务只能在检测到连接断开后采取行动，不能依赖浏览器关闭通知一定送达。客户端应显示连接恢复和等待状态。
- 服务重启时恢复最后持久化状态并保持暂停，不在启动时自动执行电脑动作；重连后由当前房主确认继续。
- 暂停原因、掉线等待、座位归属和实际操作控制权分开表达，避免通过切换连接错误地解除暂停或覆盖座位。

### 持久化概念

- 房间信息：房间身份、副号、房主、加入顺序、累计分和暂停状态。
- 参与者信息：重连身份、昵称、座位归属与恢复所需信息；网络连接视为可重新建立的临时资源。
- 牌局信息：四家原始及剩余手牌、局况、发牌人、叫牌记录、定约、当前墩、已完成墩、行动方与状态版本。
- 操作及结果信息：去重标识、动作顺序、已确认结果、结算和下一副准备状态。
- 内部存档允许保存完整牌局以便恢复，但所有对外读取都必须经过身份授权和可见状态转换。

## Testing Decisions

### 主要测试入口（已确认）

以**对局应用服务公开入口**为主要测试位置：用不同身份提交玩家操作，断言各身份能读取的状态、得分、记录及错误。测试通过公开行为构造对局，不依赖私有方法、内部对象布局或某个函数被调用几次。

围绕这一入口使用可控的发牌和时钟来稳定复现边界；存储与恢复场景使用真实临时 SQLite 数据库。项目已初始化 React、TypeScript 与 Vite 前端工程，尚无业务代码、业务测试工具或既有业务测试入口。

规则和电脑策略中的复杂组合可补充模块公开接口测试，但以对局行为为主要验收依据。浏览器端只补充关键流程：入房选座、叫牌出牌、明手控制、结算准备、重连及手机操作。具体测试工具由实施时选择。

### 验收场景

| 编号 | 场景 | 可观察的通过条件 |
|---|---|---|
| T01 | 全新服务端部署 | 在符合交付目标的 Windows 环境解压双击启动，显示可访问地址，无需安装开发工具；另一台局域网设备浏览器可进入 |
| T02 | 离线运行 | 阻断互联网并清除浏览器缓存后，页面、资源、房间与电脑对局仍可用 |
| T03 | 1～4 真人组合 | 四种人数均能开局，电脑恰好补齐空位，并完成一副牌到结算 |
| T04 | 房间与座位授权 | 重复昵称及非法占座被拒绝；不同房间不能相互读牌或操作；猜测昵称不能取回身份 |
| T05 | 中途加入 | 新玩家在当前副不能接替电脑或看到暗牌；下一副只可接替未被真人占用的电脑座位 |
| T06 | 叫牌合法性 | 定约叫品、Pass、加倍和再加倍遵循轮次与合法条件；非法叫牌不改变已确认状态 |
| T07 | 叫牌结束 | 全体不叫及定约成立均进入正确后续状态，不死锁、不错误安排打牌 |
| T08 | 庄家与明手 | 正确确定庄家和首攻方；明手在正确时点公开，仅庄家控制者可操作明手 |
| T09 | 出牌与赢墩 | 越权、越轮次、重复出牌及违反跟牌规则的操作被拒绝；合法牌局推进并完成全部墩 |
| T10 | 独立计分 | 以独立推导的固定牌例验证有局与无局、成约与宕约、加倍与再加倍等计分，不用被测计分函数生成期望值；南北、东西累计分正负对称 |
| T11 | 副号与准备 | 发牌人及局况完成 16 副轮换；未满足准备条件不开始下一副；电脑接管的离线座位自动准备，全员离线不自动开新副；累计分不随换人清零 |
| T12 | 信息隔离 | 分别读取各身份的初始、实时及重连数据，确认仅含授权信息；结束后按需求可查看四家手牌 |
| T13 | 电脑信息限制 | 保持电脑可见信息与随机性相同，改变合法可能的实际暗牌，电脑输入及策略结果不受服务器暗牌变化影响 |
| T14 | 电脑完整性 | 电脑能够完成约定表覆盖的叫牌及打牌场景；批量固定牌例无非法动作或无法继续的牌局 |
| T15 | 重复与过期操作 | 同一操作重试只生效一次；过期操作被拒绝并可获取最新状态；累计分和副号不重复增加 |
| T16 | 短暂与持续掉线 | 用可控时间验证 30 秒之前不接管，达到等待时间后接管；原玩家回归后控制权正确、已完成动作不撤回 |
| T17 | 电脑结果竞态 | 思考期间发生暂停、重连或状态推进，旧电脑结果不会执行；下一次有效动作仍可正常提交 |
| T18 | 房主转交 | 房主掉线达到等待时间后，最早加入且在线的真人获得权限；全员离线后按相同规则从已重连真人中选出继任者，仍须手动恢复；其他玩家不能越权暂停或恢复 |
| T19 | 全员离线 | 单机关闭页面或最后一名真人离线被检测后暂停保存，电脑不继续推进；恢复后保持暂停至房主确认 |
| T20 | 服务重启 | 在叫牌、打牌和结算阶段分别重启，恢复最后提交的位置、累计分和身份归属，保持暂停且不重算操作；已有离线截止时间跨重启保留 |
| T21 | 存储失败与确认丢失 | 未提交操作不被确认成功；提交后响应丢失再重试，结果一致且不重复执行 |
| T22 | 多桌运行 | 10 桌含电脑对局并发，无跨房间串牌、牌局停滞或操作丢失；记录硬件、耗时、资源占用及瓶颈 |
| T23 | 浏览器主流程 | 多个独立浏览器身份完成入房至结算并重连；手机视口能读取手牌、选择叫品和出牌，无关键控件遮挡；界面遵循 Open Design 参考稿的视觉方向与操作反馈 |

### 测试结论的边界

- 前端工程初始化与构建检查不等于业务验收；当前尚无桥牌业务实现，T01～T23 尚未执行。
- 10 桌并发验证用于检查功能稳定性，不设置待用户确认的硬件基线或延迟阈值；macOS 上的验证结果不能替代 Windows 部署与离线运行验收。
- 合法出牌和稳定完局只能证明规则与流程正确，不能证明普通牌友水平。牌力需要独立评估。
- 已确认的测试入口作为后续拆票与实施的验收依据。

## Out of Scope

- 公网大厅、陌生人匹配、账号注册与第三方登录。
- 原生桌面或手机客户端、玩家安装包、Windows 服务端安装向导。
- 观战、策略推荐、悔牌、可自定义叫牌体系。
- 多桌比赛排名、盘式桥牌计分，以及将房间累计分转换为竞技排名的功能。
- 运行时依赖云端模型、在线资源或互联网服务。
- 第一阶段保证普通牌友或更高水平的电脑牌力，以及训练大规模模型。
- 第一阶段将 BEN、DDS 等候选作为未经验证的必选依赖。
- 线下裁判裁决、纠违补偿及认证赛事完整管理。
